## Local entry identity

Tag assignments and collection references share a local entry key. It resolves aliases in the parent directory and preserves a final symlink as its own directory entry. Files reached through `/data/user/0` and `/data/data`, or through a symlinked parent folder, therefore share organization metadata. A selected symlink keeps its own tags; its target and children reached through that link remain separate entries. Hard links keep distinct path identities.

Catalog reads normalize existing version-1/version-2 locations in memory, union tag assignments for equivalent keys, and deduplicate collection membership while preserving order. Opening the catalog does not rewrite it. If a parent cannot be resolved, its normalized saved spelling is retained; a later authorized read can resolve and merge it. Migration uses the currently available filesystem, not a history of external symlink changes. A successful metadata mutation publishes the normalized catalog through the existing staged, synced replacement. Writers using equivalent parent paths to the catalog share the same publication lock. Primary tag-color ordering stays stable across writes and reloads.

App-initiated rename, move, copy, recovery and Undo/Redo use the same keys. Moves remap recorded descendants, copies carry tags without joining collections, and renaming a directory symlink moves its own metadata without moving its target's child metadata. Browsing, grouping, tag filters, context actions and reviewed rename/tag previews use the entry key rather than the visible path spelling.

This remains location-based metadata, not persistent inode tracking. External replacement at the same path can occupy that reference. An external move to a different path requires a reviewed relink. Symlink retargeting does not transfer metadata from the saved canonical target to an unrelated target. Canonicalization checks filesystem metadata; it does not open file payloads. Large-catalog startup/memory/device benchmarks remain open roadmap work.

## Saved locations

The catalog includes both tag-only locations and collection-only references, including unavailable entries. Search matches saved paths, tag names and collection names. Equivalent local path spellings are recognized when searching by an absolute path. It does not claim a persistent index of provider filenames or document contents.

Only one page of at most **200 locations** is checked at a time. Previous/Next controls show the current range and total matches. Cancellation and backgrounding stop metadata preparation without deleting a saved location. Failed metadata reads remain visible with their reason. A missing local file is distinguished from a location that needs storage access. Full-path details, copy-location, Show in folder, storage recovery and relinking remain available as appropriate.

## Choosing a replacement

**Locate replacement…** opens a separate read-only browser. Browse Workspace, authorized tablet storage or connected provider roots; use parent navigation, search/hidden controls, or enter a complete local path/provider URI. Select a file, or open a folder and choose **Use this folder**. The browser streams children through the existing cancellable loader. Initial limits are 1,000 results / 50,000 scanned entries; Load more increases them up to 20,000 results / 200,000 scanned entries. Partial, pending and failed listings remain explicit. Search or a complete path can reach a known item outside an earlier result budget. Known items receive an independent metadata check before review.

A replacement needs readable metadata, not provider write access. Relinking does not write the replacement file, copy data, move originals or create storage grants. It can use a read-only provider document that is already authorized. An unauthorized or unavailable replacement cannot be committed.

## Review, apply and Undo

The review freezes the current library, original location status and replacement metadata. It displays complete source/target paths, replacement type/size/access, source and destination tag changes, and every affected collection in a scrollable review. No mutation occurs while choosing or reviewing.

Relinking changes **every exact reference** to the saved key across collections. Existing replacement membership is deduplicated. **Carry saved tags to replacement** merges source tags with existing replacement tags and removes the source assignment. Turning it off leaves the source tags in place and only changes collection references. Other tags, collection members and original files are preserved.

Folder descendants and different provider document IDs are separate saved locations. The tool does not guess opaque provider IDs or construct unverified child URIs. A saved provider spelling stays the reference key even if a metadata query returns a canonical/different URI; Locate replacement remains available to review and relink that saved key explicitly. Review those locations individually through Saved locations. Known app-initiated provider routes continue to use the existing remapping behavior; externally changed/opaque identities are repaired explicitly.

Apply rechecks replacement revision/access and the original location's status/revision, then compares the whole reviewed organization snapshot before atomic publication. A changed replacement, reappearing original or later catalog edit requires another review. The entry key is checked alongside the filesystem revision, so retargeting a parent alias to another hard-link entry cannot pass merely because inode, bytes and timestamps match. History records the actual normalized snapshot published under the store lock. The review and selection survive activity recreation without replaying Apply. Cancellation stops preparation; an atomic commit already in progress finishes through the operation runtime.

The operation records one protected **Relink saved location** history command. Undo/Redo restore both tag assignments and collection membership together and refuse to overwrite later organization edits. History remains session-scoped and does not survive process death. After success, open collection/tag views and the Saved locations page refresh. These checks are not a filesystem-wide transaction; provider metadata can still race individual calls.
