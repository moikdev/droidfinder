## Collections

A collection stores references to existing locations. Creating one or adding reviewed items does not copy or move the original files. Open a collection in the normal explorer to use list/icon/column/gallery views, tabs, search filters, Peek and ordinary file commands. The sidebar shows the first six collections plus an active collection outside that group; the searchable manager includes the entire catalog. IDs stay stable when a collection is renamed or recolored, including tabs and independent windows opened on it.

File commands in a collection act on the **original files**. To leave originals in place, select reference checkboxes in Organize and choose **Remove references**. Deleting a collection removes its references, not the files or their tags. Both changes support protected session Undo/Redo.

Members are explicit locations, not recursive rules. Referenced folders open normally; filtering a collection evaluates its members rather than automatically searching every referenced folder's descendants. Use a Smart Folder for a live recursive rule. Duplicate references are removed. The manager checks metadata with cancellable progress and keeps missing, disconnected and inaccessible references visible with their reported problem. The Unavailable filter, full-location details, copy-location, storage recovery and Show in folder actions help review them. Failed references are never silently deleted.

References follow the routes recorded by app-initiated moves, renames, recovery and Undo/Redo. Copying a file copies its tags without automatically adding the copy to its collections. Paths remain location references, rather than persistent inode aliases: outside moves can leave a reference unavailable, and a replacement at the same saved path can appear at that location. Since [0.24.0](REFERENCES.md), equivalent parent aliases share organization keys and saved references can be relinked through a complete review; final symlinks remain distinct entries. Provider-controlled identities and opaque child-ID changes can require manual review; local and path-like provider descendant remapping are covered by the tests.

## Tag library and selection review

The library has name search, usage counts, six color choices, create/edit/rename, Browse and reviewed deletion. Deletion shows its assignment count and checks that the reviewed catalog did not change before committing. Other tags and original files are kept. Saved searches that use a deleted tag retain their criterion; restoring the tag with Undo restores that match. Tag names support Unicode, with conservative canonical/case-equivalent name uniqueness.

The Selection page captures the original file selection. Each tag can **Keep**, **Add**, or **Remove** assignments; Keep preserves mixed assignments across files. **Clear existing tags first** is an explicit rule. The complete scrollable review shows current/result tags, source locations, unchanged rows, exclusions and unavailable items. Filtering hides rows without changing the apply scope. Exclude unavailable items to apply a valid subset. Opening the tool and editing a draft do not write tags.

Apply rechecks source metadata/revision, catalog definitions and the selected items' current assignments. A changed source or selected assignment requires another review. Unrelated assignments are included from the current store and preserved. Read-only provider files can receive tags because tags are app metadata; the app still requires access to read their metadata. No payload modification or additional provider write grant is needed. The review, rules and selection survive activity recreation. Stop cancels preparation; atomic metadata commits finish once publication has begun. Backgrounding stops review reads without replaying a mutation. Closing Organize or opening a collection explicitly restores explorer focus so keyboard shortcuts can resume without clicking the file list.

Tag and collection edits use the shared session history. History checks its expected metadata state before Undo/Redo so a later edit cannot be silently replaced. History is session-scoped, limited to the existing 50-command history, and does not survive process death. Large-library memory/performance benchmarks and persistent recovery remain roadmap work.

## Reviewed JSON export

The export action captures a metadata snapshot and displays counts before choosing a destination. Export the entire library or only reviewed locations. A selection export omits unrelated tag definitions, assignments and collection members; untagged selected locations remain explicit records. The export contains tag names/colors, assignments, collection IDs/names/colors and locations. Workspace paths are relative; other local paths and provider URIs remain explicit. It contains no file contents, credentials or Android storage grants.

Names and locations can reveal private organization details, so the review describes the included scope. This is an organization metadata export, not a backup of the original files. Import, per-location rebinding and broader settings/workspace backup/restore remain separate roadmap work.

The destination picker retains the current folder while metadata loads, including a read-only current folder. It reports loading, read-only, permission and listing failures. Save is disabled until that exact destination is known writable; selecting another root cannot reuse the previous root's status or rows. Saving stages the JSON, uses a keep-both name when a file already exists, cleans failed staging where the provider permits it, and records protected Undo/Redo for the exported file. Filename, scope and the captured snapshot survive activity recreation; a failed export remains available for targeted retry.

## Persistence and bounds

Tags and collections share the app-private `tags.properties` catalog. Existing version-1 tag data is read; successful writes publish version 2. Writes reload and serialize access, validate a complete candidate, stage and sync the bytes, and replace the catalog before exposing the new in-memory state. Unknown versions/fields, invalid catalogs and files larger than 16 MiB are preserved and block metadata writes. An invalid catalog does not crash startup or turn into an empty writable library. Repairing the file and refreshing reloads it.

File operations retain their real results when organization metadata cannot follow a published change. A shared review notice preserves the failure reason, and unavailable references can be inspected. The original library is kept; this does not promise a filesystem-wide transaction or a durable metadata-recovery journal.

Limits are 256 tags (48-character names), 128 collections (64-character names), 10,000 members per collection, 100,000 collection references in total, 100,000 tagged locations, and a 16 MiB encoded catalog. Selection review supports 10,000 items. Exports are limited to 32 MiB. Bounds fail explicitly before exposing a partial saved state. These are safety ceilings, not measured performance guarantees. Auxiliary destination child-list paging and physical provider/device measurements remain open.

Older APKs do not understand collection metadata. Android normally prevents version-code downgrades; forcing an older build can discard newer catalog fields when it writes tags. Export before changing builds, and use the current preview for this format.

## Validation

Current local results: 220 JVM tests (0 failures/errors/skips), optimized preview and unsigned-release builds, and lint with 0 errors / 125 warnings / 11 hints. Twenty new domain cases cover catalog migration/corruption, encoded bounds, Unicode names, serialized writers, guarded history, reference relocation, scope-preserving tag rules and metadata-only export, including canonical/alias Workspace roots.

The combined native run before the final export/focus adjustments passed all 65 cases on the dedicated Android 16 / API 36 emulator: 17 organization, 13 rename, ten Finder, five provider, eight Workspace-provider, one advanced-tag, three folder-merge/tag, one Workspace-move metadata and seven navigation cases. These cover mixed tag review, frozen state/recreation, changed sources/assignments, read-only provider tagging, cross-root collections, normal browsing/tabs/windows, reference remapping and guarded Undo/Redo, unavailable locations, native editors, corrupt catalogs, export collisions/retry/staging cleanup and a read-only destination. After the pure export alias fix, both native export workflows passed again (2 tests). After the final keyboard-focus restoration, all 18 organization and nine Windows-shortcut workflows passed together (27 tests), including physical Ctrl+L events after closing Organize and opening a collection.

The initial 13-case run exposed fixture timing and ambiguous selectors; those were corrected and the class passed. A subsequent 64-case run exposed the picker default-folder race and two test-selector/path assumptions. The picker now retains the current folder while its status loads, selectors target actual controls, and the path check compares canonical identity. Three affected cases passed together before the final 65-case run.

In the final optimized preview, manual QA created a green Research library containing three synthetic files from Planning and References, added Green while preserving a mixed Blue assignment, and exercised Ctrl+Z/Ctrl+Y. It exported the reviewed selection through the real Android Documents provider into the dedicated QA folder in Documents. The pulled 1,333-byte JSON was parsed and checked: selection scope, exactly two tag definitions, three assignment records, one collection with three members, and relative Workspace paths for both Android path spellings. Every record retained Green and exactly one retained Blue. No file payloads were exported.

The optimized preview was visually checked in light and dark appearance and while changing to a 640 × 800 dp tablet window with Organize open. Narrow tag choices/review pages and collection member navigation kept their footer controls visible. A removal rule was previewed without applying it; the tag catalog still showed Green on all three files. The normal 1920 × 1200 / 240 dpi display and light appearance were restored. Screenshots use synthetic QA files. Hosted GitHub runners are not used; phone-specific layout remains deferred.
